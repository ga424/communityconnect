# S-1 Submit and track a maintenance request: design doc

## 1. Problem

Residents ask managers for updates on requests that were already handled (E-1, E-2), and residents who cannot see a request’s status come to the office to ask (E-12). Residents need to submit a request and see its status themselves.

## 2. Scope

- A resident submits a request for their own unit, in a community where they are a resident, with a category and a description.
- A resident lists the requests they submitted in that community, newest first.
- A resident opens one of their own requests and sees its status.

## 3. Non-goals

- No status changes or reopening (S-2), no photos (S-11), and no editing or deleting a submitted request.
- No real sign-in (passwords, sessions, accounts); see D1.
- No email or portal notifications when a request is submitted.

## 4. Interface

All paths are under the FastAPI app in `app/main.py`. Every endpoint reads the caller from the `X-User-Id` header (D1). Every error body is `{"detail": <message>}`.

| Endpoint                                        | Request                                                                       | Success                            | Errors                                                                                                                                                            |
|-------------------------------------------------|-------------------------------------------------------------------------------|------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `POST /communities/{community_id}/requests` | path `community_id: int`; JSON body `{"category": str, "description": str}` | `201`, body `RequestOut`           | `401 "Unknown user"`; `404 "Not found"`; `422 "Invalid request body"`; `422 "Description is required"`; `422 "Description is too long"`; `422 "Unknown category"` |
| `GET /communities/{community_id}/requests`  | path `community_id: int`                                                    | `200`, body `list[RequestOut]` | `401 "Unknown user"`; `404 "Not found"`                                                                                                                           |
| `GET /requests/{request_id}`                | path `request_id: int`                                                      | `200`, body `RequestOut`           | `401 "Unknown user"`; `404 "Not found"`                                                                                                                           |

`RequestOut` = `{"id": int, "community_id": int, "unit_id": int, "category": str, "description": str, "status": "Open" | "In progress" | "Resolved", "created_at": str}`.

## 5. Data

| Entity     | Fields, types and rules                                                                                                                                                                                                                                                                                                                                                                                                                           |
|------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Community  | id: int, ≥ 1, unique; name: str, 1 to 100 characters, unique                                                                                                                                                                                                                                                                                                                                                                                      |
| Unit       | id: int, ≥ 1, unique; community_id: int, an existing Community; label: str, 1 to 20 characters, unique within its community                                                                                                                                                                                                                                                                                                                       |
| User       | id: int, ≥ 1, unique                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Membership | user_id, community_id: int, one row per user and community; role: str, `resident`, `board_member`, `manager` or `admin`; unit_id: int or null, required for `resident`, in the same community                                                                                                                                                                                                                                                     |
| Request    | id: int, ≥ 1, assigned by the system; community_id: int, the community in the path; unit_id: int, the submitter’s unit in that community; submitted_by: int, the caller’s user id; category: str, exactly one value of REQUEST_CATEGORIES; description: str, 1 to MAX_DESCRIPTION_CHARS characters after trimming, stored trimmed; status: str, `Open`, `In progress` or `Resolved`, `Open` when created; created_at: str, UTC, set by the system |

## 6. Rules

- **R1 (invariant):** Every request returned to a resident has `submitted_by` equal to that resident’s user id and `community_id` equal to a community where they hold the `resident` role.
- **R2 (invariant):** For a request the caller may not see, every endpoint returns exactly what it returns for an id that does not exist: status `404` and body `{"detail": "Not found"}`.
- **R3 (precondition):** `POST` succeeds only if the caller holds the `resident` role in `community_id`. Otherwise it returns `404 "Not found"`.
- **R4 (postcondition):** After a successful `POST`, the new request has status `Open`, appears first in the caller’s list for that community, and the total number of requests has grown by exactly 1.
- **R5 (postcondition):** After any rejected `POST`, the total number of requests is unchanged.

## 7. Edge cases

- A description of only spaces, or one that fits MAX_DESCRIPTION_CHARS only after trimming.
- A resident of two communities, and a request id belonging to another community or to a neighbor.
- A category in a different case, such as “plumbing”.
- A missing, non-numeric or unknown `X-User-Id`, and a non-numeric path id.

## 8. Decisions and open questions

**Decisions**

- **D1:** The caller is the user named by the `X-User-Id` header, which must match `^[1-9][0-9]*$` and name an existing User, otherwise `401 "Unknown user"`. An existing user with no membership in the community gets `404 "Not found"`.
- **D2:** A resident sees only the requests they submitted, not their neighbors’.
- **D3:** Hidden and missing records both return `404 "Not found"`, never `403`.
- **D4:** Category matching is exact and case-sensitive.
- **D5:** Times are stored in UTC and returned as `YYYY-MM-DDTHH:MM:SSZ`.
- **D6:** Checks run in this order, and the first failure is returned: caller (401), path and membership (404), body shape, description, category (422).
- **D7:** Every error body is `{"detail": <message>}`, including framework validation errors. A non-numeric path id returns `404 "Not found"`. Malformed JSON, a missing field, or a non-string `category` or `description` returns `422 "Invalid request body"`; extra fields are ignored.
- **D8:** Settings are in `app/settings.py`, with provisional defaults REQUEST_CATEGORIES = `["Plumbing", "Electrical", "Landscaping", "Pool", "Other"]`, MAX_DESCRIPTION_CHARS = `2000`. Tests read the settings, never these values.
- **D9:** Trimming is Python’s `str.strip()`, and length is `len()` of the trimmed string.
- **D10:** The three endpoints serve callers with the `resident` role in the community; managers, admins and non-members who are not residents get `404 "Not found"`. Board members who are not residents are OQ2.
- **D11:** Lists are ordered by `created_at`, newest first, then `id` descending, with no pagination.
- **D12:** Storage is PostgreSQL 14 or newer, reached with `psycopg` 3 at DATABASE_URL, in the schema DATABASE_SCHEMA; data persists across restarts, and each test uses a new empty schema that is dropped afterwards.
- **D13:** Communities, units, users and memberships are created by functions in `app/seed.py`, with no endpoints. Tests set a status with `tests/helpers.py::set_status(request_id: int, status: str) -> None`, which the API does not expose.

- **D14:** Exactly one `X-User-Id` header is read as is, without trimming; a repeated header gets `401 "Unknown user"`. Path ids must match `^[1-9][0-9]*$` and be at most 9223372036854775807, otherwise `404 "Not found"`.
- **D15:** The body must be a JSON object; an empty body, invalid JSON, an array or `null` gets `422 "Invalid request body"`. Content-Type is not checked. A trimmed description of length 0 gets "Description is required"; one longer than MAX_DESCRIPTION_CHARS gets "Description is too long".
- **D16:** Python 3.11+, FastAPI and `psycopg` 3 (no ORM); dependencies are listed in `requirements.txt`. `app.main.create_app() -> FastAPI` calls `app.db.init_db()`, which creates DATABASE_SCHEMA and the §5 tables if missing, with foreign keys; `app.main:app` is the instance for uvicorn. DATABASE_URL comes from the environment variable `COMMUNITYCONNECT_DATABASE_URL`, default `postgresql://postgres:postgres@localhost:5432/communityconnect`, and DATABASE_SCHEMA from `COMMUNITYCONNECT_DB_SCHEMA`, default `public`. The code reads `app.settings` attributes when it uses them, never copies them at import. Every API call and seed call opens its own connection and commits before closing it; ids are `BIGINT GENERATED ALWAYS AS IDENTITY`, and `created_at` is stored as text in the D5 format.
- **D17:** `app/seed.py` has `create_community(name: str) -> int`, `create_unit(community_id: int, label: str) -> int`, `create_user() -> int` and `add_membership(user_id: int, community_id: int, role: str, unit_id: int | None = None) -> None`. Each one enforces the §5 rules and raises `ValueError` on a violation. Nothing is seeded at startup.
- **D18:** Tests use `fastapi.testclient.TestClient(create_app())` against the database in `COMMUNITYCONNECT_TEST_DATABASE_URL` (default `postgresql://postgres:postgres@localhost:5432/communityconnect_test`), with DATABASE_SCHEMA set to a new schema for each test. If that server cannot be reached, every test fails with a message naming the URL. `tests/helpers.py` also has `count_requests() -> int`, used for R4 and R5; both helpers connect with DATABASE_URL and DATABASE_SCHEMA.
- **D19:** Until OQ2 is answered, a board member without the `resident` role gets `404 "Not found"`, as in D10. Work that depends on an open question is left unbuilt and raised with the team; the rest of the task continues.
- **D20:** `unit_id` is taken from the caller's membership when the request is submitted, never from the body, and is never changed afterwards. A resident with no requests gets `200 []`. There is no limit on submissions, and two identical submissions are two requests.
- **D21:** An unsupported method gets `405 {"detail": "Method Not Allowed"}`, and an unknown path gets `404 {"detail": "Not found"}`, with no trailing-slash redirect. `POST` sends no `Location` header, and its 201 body is the `RequestOut` that `GET` returns. This story adds no CORS, logging or rate limiting.

**Open questions**

- **OQ1:** Can a tenant who is not the owner submit a request for the unit they rent (Q-5, S-9)? Do not build anything that depends on this. Stop and ask.
- **OQ2:** Should board members see every request in their community? Do not build anything that depends on this. Stop and ask.
