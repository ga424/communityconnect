# S-6 Scheduled monthly dues payment: design doc

## 1. Problem

Most late payers simply forgot (E-21), and paying by two channels caused a double payment that took three weeks to refund (E-9). Residents need one scheduled payment that can never be charged twice for a month.

## 2. Scope

- A resident schedules an automatic payment for their unit (method, test token, day of the month), and the resident and manager see the unit’s payment history.
- A daily run charges each scheduled unit once a month through Stripe test mode, retrying a declined charge after RETRY_DELAY_DAYS, up to MAX_PAYMENT_ATTEMPTS attempts.

## 3. Non-goals

- No real money (Stripe test mode only), no overdue flags or reminders (S-7), and no dues report (S-8).
- No changing, pausing or cancelling a schedule, and no partial payments, late fees or card fees (OQ1).

## 4. Interface

| Endpoint or function                                                                                | Input                                                                                     | Success                                                                                     | Errors                                                                                                                                                                                 |
|-----------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `POST /communities/{community_id}/payment-schedules`                                            | path `community_id: int`; JSON `{"method": str, "day_of_month": int, "token": str}` | `201`, `ScheduleOut`                                                                        | `401 "Unknown user"`; `404 "Not found"`; `409 "Schedule already exists"`; `422 "Invalid request body"`; `422 "Unknown method"`; `422 "Day must be 1 to 28"`; `422 "Token is required"` |
| `GET /communities/{community_id}/payment-schedules/mine`                                        | path `community_id: int`                                                                | `200`, `ScheduleOut`                                                                        | `401 "Unknown user"`; `404 "Not found"`                                                                                                                                                |
| `GET /communities/{community_id}/payments?month=YYYY-MM`                                    | path `community_id: int`; query `month: str`                                            | `200`, `list[PaymentOut]`                                                               | `401 "Unknown user"`; `404 "Not found"`; `422 "Invalid month"`                                                                                                                         |
| `run_due_payments(today: date) -> RunResult`                                                | `today: datetime.date`                                                                  | `RunResult(charged: int, failed: int, skipped: int)`                                    | none; see D16                                                                                                                                                                          |
| `record_manual_payment(unit_id: int, billing_month: str) -> Payment`                    | as typed                                                                                  | the new `Paid` Payment                                                                      | `AlreadyPaid`                                                                                                                                                                          |
| `Processor.charge(token: str, amount_cents: int, idempotency_key: str) -> ChargeResult` | as typed                                                                                  | `ChargeResult(status: str, processor_id: str)`; status is “succeeded” or “declined” | `ProcessorUnavailable`                                                                                                                                                                 |

`ScheduleOut` = `{"id": int, "unit_id": int, "method": str, "day_of_month": int, "active": bool}`; `PaymentOut` = `{"id": int, "unit_id": int, "billing_month": str, "amount_cents": int, "method": str, "status": str, "attempt": int, "created_at": str}`.

## 5. Data

| Entity    | Fields, types and rules                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
|-----------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Community | dues_amount_cents: int, \> 0, required (this is DUES_AMOUNT_CENTS); S-1’s other entities are reused unchanged                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Schedule  | id: int, unique; unit_id: int, at most one schedule per unit; method: str, `ach`, `debit` or `credit`; day_of_month: int, 1 to 28; token: str, non-empty, never returned by the API; active: bool, `true` when created; created_at: str, UTC                                                                                                                                                                                                                                                                                       |
| Payment   | id: int, unique; unit_id: int, an existing unit; billing_month: str, `YYYY-MM` with month 01 to 12; amount_cents: int, the community’s dues_amount_cents when charged; method: str, `ach`, `debit`, `credit` or `manual`; status: str, `Pending`, `Paid` or `Failed`; attempt: int, 1 to MAX_PAYMENT_ATTEMPTS (1 for manual); idempotency_key: str, unique, `"{unit_id}:{billing_month}:{attempt}"` or `"{unit_id}:{billing_month}:manual"`; processor_id: str or null (null for manual); created_at: str, UTC |

## 6. Rules

- **R1 (invariant):** For every unit and billing month there is at most one Payment with status `Paid`, whatever its method.
- **R2 (invariant):** No two Payments share an idempotency key, and each processor call uses the key of the Payment it records.
- **R3 (precondition):** `run_due_payments` creates no Payment for a unit that already has a `Paid` Payment for the month, including a `manual` one.
- **R4 (postcondition):** After `run_due_payments(today)`, every due schedule (D18) whose month is not `Paid` has exactly one attempt-1 Payment for the month: `Paid`, `Failed`, or `Pending` if the processor was unavailable.
- **R5 (postcondition):** A unit whose latest attempt is `Failed` and below MAX_PAYMENT_ATTEMPTS gets exactly one new attempt on the first run at least RETRY_DELAY_DAYS after that attempt, and none earlier.

## 7. Edge cases

- The run is interrupted after the processor charged a unit but before its Payment was saved as `Paid`, then restarted.
- A manual payment recorded on the day of the run, or after a declined charge but before its retry.
- A schedule created after its chosen day this month; a `day_of_month` of 29 to 31; the processor unreachable.

## 8. Decisions and open questions

**Decisions**

- **D1:** `day_of_month` is 1 to 28, so every month has the chosen day. **D2:** The current month’s charge is the community’s dues_amount_cents; residents cannot enter an amount. Card fees are OQ1; earlier months are OQ3. **D3:** All money is integer cents.
- **D4:** Each attempt is saved as `Pending` with its key before the processor call, then set to `Paid` or `Failed` (for ACH, see OQ2). On restart a `Pending` Payment is charged again with the same key, so the processor returns its earlier result. **D5:** `today` is a UTC date passed to `run_due_payments`; every `created_at` comes from `app/clock.py::now()`, which tests replace.
- **D6:** S-1’s D1, D3, D6, D7 and D12 apply (identity, hidden records, check order, error format, storage). **D7:** Only a caller with the `resident` role in the community can create or read a schedule, and it is for their unit there.
- **D8:** In the payments list a resident sees their own unit and a manager every unit they manage; admins and non-members get `404 "Not found"`; board members are OQ4. All attempts are listed by unit_id, then attempt.
- **D9:** `month` is required and must be `YYYY-MM` with month 01 to 12, otherwise `422 "Invalid month"`; a future month returns an empty list. **D10:** “Payments page” in AC-18 means the response of `GET .../payment-schedules/mine`; no user interface is built.
- **D11:** A schedule cannot be changed, paused or cancelled, so `409 "Schedule already exists"` applies to any existing schedule for the unit. **D12:** Fields are checked in the order method, day_of_month, token; a missing field or wrong type is `422 "Invalid request body"`. Tokens are not checked with Stripe when saved; a bad one is declined at charge time.
- **D13:** Manual payments are recorded only by `record_manual_payment`, which creates a `Paid` Payment or raises `AlreadyPaid` if the month is already `Paid`. **D14:** dues_amount_cents values are set by `app/seed.py`. **D15:** `app/settings.py` holds provisional defaults RETRY_DELAY_DAYS = `3` and MAX_PAYMENT_ATTEMPTS = `2`, from our proposal, not from interviews; tests read the settings, never these values.
- **D16:** `ProcessorUnavailable` leaves the Payment `Pending` without using an attempt, and the next run retries the same key. `charged` and `failed` count Payments that became `Paid` or `Failed` in the run, retries included; `skipped` counts due schedules left unpaid because the month was `Paid` or the processor was unavailable. **D17:** A retry is due RETRY_DELAY_DAYS after the `today` of the run that made the failed attempt, for the same billing_month. After the last allowed attempt fails, nothing more happens that month; the schedule stays active.
- **D18:** A schedule is due on each run from its day_of_month to the month’s end while the unit has no Payment that month, so a missed run is caught up. A new schedule is first due in the first month whose chosen day is after its created_at date.
- **D19:** `python -m app.run_payments` calls `run_due_payments` with today’s UTC date; scheduling that command is out of scope. **D20:** `StripeTestProcessor` uses PaymentIntents in test mode (key in STRIPE_TEST_KEY); a card error is `declined`, and a connection error or 5xx raises `ProcessorUnavailable`. Tests use only `FakeProcessor`; processor_id is stored.

- **D21:** `method` must be exactly `ach`, `debit` or `credit` (case-sensitive; `manual` is "Unknown method"). `day_of_month` must be a JSON integer, not a bool, float or string, otherwise "Invalid request body"; an integer outside 1 to 28 is "Day must be 1 to 28". The token is not trimmed; an empty or whitespace-only token is "Token is required".
- **D22:** `POST` runs S-1's 401 and 404 checks, then the D12 body checks, then the 409 check. A unit has at most one schedule, whichever resident of it creates it. `GET .../mine` with no schedule returns `404 "Not found"`.
- **D23:** "Every unit they manage" means every unit in a community where the caller has the `manager` role. The list includes `Pending`, `Paid` and `Failed` Payments with the `PaymentOut` fields only, ordered by unit_id, then attempt, then id.
- **D24:** `app/clock.py::now() -> datetime` returns a timezone-aware UTC datetime; every `created_at` is formatted as in S-1's D5.
- **D25:** A run handles only active schedules, and only the billing_month of `today` (earlier months are OQ3). A schedule is due when `today.day >= day_of_month` and the date with that day in `today`'s month is strictly after the schedule's `created_at` UTC date. For a due schedule the run does the first of these that applies: if the month is `Paid`, it skips the schedule; if there is no Payment, it makes attempt 1; if the latest attempt is `Failed`, it applies D17.
- **D26:** At the start of every run, every `Pending` Payment from any month is charged again with its own key and keeps its attempt number. A `Pending` Payment whose month already has a `Paid` Payment is left as it is (OQ5).
- **D27:** `record_manual_payment` raises `PaymentPending` and records nothing while the month has a `Pending` Payment (OQ5), and raises `ValueError` for an unknown unit or an invalid billing_month. When the month has only `Failed` attempts it records the payment. Its amount is the community's dues_amount_cents at that moment.
- **D28:** `app/payments.py` holds `run_due_payments`, `record_manual_payment`, `RunResult`, `AlreadyPaid` and `PaymentPending`. `app/processor.py` holds `Processor`, `ChargeResult`, `ProcessorUnavailable`, `FakeProcessor`, `StripeTestProcessor`, `get_processor() -> Processor` and `set_processor(p: Processor) -> None`; the default processor is `StripeTestProcessor`, and `run_due_payments` uses `get_processor()`.
- **D29:** `FakeProcessor(declined_tokens: frozenset[str] = frozenset(), unavailable: bool = False)` stores one result per key. A repeated key returns the stored result and charges nothing, even if the amount or token differs. `calls` lists every `(token, amount_cents, idempotency_key)` it received.
- **D30:** A Payment's amount_cents is the dues_amount_cents at the moment the Payment is created; a charge that is retried after a restart uses the stored amount. `app/seed.py::set_dues(community_id: int, dues_amount_cents: int) -> None` raises `ValueError` unless the value is > 0. A community with no dues set has no due schedules.
- **D31:** The run keeps going after `ProcessorUnavailable` for one unit. Every change to a Payment is committed as soon as it is made. Any other exception stops the run; this is how AC-20 simulates a crash.
- **D32:** The tables are `schedules` and `payments` in PostgreSQL (S-1 D12), with the §5 field names; `init_db()` runs `ALTER TABLE communities ADD COLUMN IF NOT EXISTS dues_amount_cents`. There is a unique index on `idempotency_key` and a partial unique index on `(unit_id, billing_month)` where status is `Paid` (R1). Only one run at a time is supported.
- **D33:** `StripeTestProcessor` charges currency `usd`, confirming at once and off-session, with the token as the PaymentMethod id. A `CardError` is `declined`; any other Stripe error stops the run. `python -m app.run_payments` reads STRIPE_TEST_KEY from the environment, exits with code 2 if it is missing, and otherwise prints `charged=N failed=N skipped=N` and exits 0.
- **D34:** Until OQ2 is answered, the tests for AC-19 to AC-22 use `debit` schedules, and nothing is built that decides how a successful ACH charge is shown.

**Open questions**

- **OQ1:** Who pays the card processing fee, the resident or the association (Q-1)? Do not build anything that depends on this. Stop and ask.
- **OQ2:** Should an ACH payment show as `Paid` before the bank’s return window of 3 to 5 business days has passed (E-10)? Do not build anything that depends on this. Stop and ask.
- **OQ3:** When a resident owes earlier months, should the scheduled payment charge only the current month? Do not build anything that depends on this. Stop and ask.
- **OQ4:** Should board members see every unit’s payments (S-8)? Do not build anything that depends on this. Stop and ask.
- **OQ5:** If a manual payment is recorded while that month’s scheduled charge is `Pending`, which stands, and is the other refunded? Do not build anything that depends on this. Stop and ask.
