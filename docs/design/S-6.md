# S-6 — draft for team review

Source: M1 Review v3, section 5. November 9 documentation reconciliation: contract behavior and acceptance criteria preserved; named design review remains pending. Current test state is recorded in section 9. Fresh AI gap check is stored alongside this design; it is not a human approval.

## 1 Problem

One owner paid twice through different channels (E-9). A treasurer attributed lateness to forgetting (E-21). We propose scheduling and duplicate-charge prevention, while willingness to save a method remains A-3. This design covers only a local simulation (A-8).

## 2 Scope

Save one test_card schedule for a seeded resident’s unit; display its schedule and monthly history; simulate due charges, same-key recovery and bounded retries. The harness uses one test billing month with no arrears. A pre-recorded manual Paid payment suppresses a charge.

## 3 Non goals

No Stripe, ACH, real money, fees, refunds, emails or reminders. No schedule editing/cancellation, concurrent workers, manual receipt during an in-flight attempt, multi-month arrears or production authentication. No provider-integration claim may be inferred from passing these tests.

## 4 Interface

HTTP identity and error envelopes follow S-1. Only a resident can create/read their own unit schedule; residents read their unit’s payments and assigned managers read payments in that community. Other roles return 404 Not found. ScheduleOut excludes token; PaymentOut includes all Payment fields below except the key.

| Interface | Typed result and failures |
| --- | --- |
| POST /communities/{community_id}/payment-schedules | community_id: int; body {method: str, day_of_month: int, token: str}; 201 ScheduleOut. 401 Unknown user; 404 Not found; 409 Schedule already exists; 422 Invalid request body / Unknown method / Invalid day / Token is required. |
| GET /communities/{community_id}/payment-schedules/mine | community_id: int; 200 ScheduleOut, or 401 Unknown user / 404 Not found. |
| GET /communities/{community_id}/payments?month=YYYY-MM | community_id: int; month: str; 200 list[PaymentOut], or 401 Unknown user / 404 Not found / 422 Invalid month. |
| run_due_payments(today: date) -> None | Raises RunInterrupted for the injected interruption; other configuration errors fail the harness before running. |
| FakeProcessor.charge(token: str, amount_cents: int, key: str) -> ChargeResult | ChargeResult {status: succeeded \| declined, processor_id: str}. The fake’s durable key store returns the same result on replay. No network call. |

## 5 Data

| Entity | Fields and constraints |
| --- | --- |
| Community | Reuses S-1; dues_amount_cents: int > 0, seeded per community (DUES_AMOUNT_CENTS). |

## 6 Rules

R1 Invariant: at most one payment is Paid per unit/month; a PostgreSQL partial unique constraint enforces it. R2 Invariant: an attempt key is stable and unique as unit_id:billing_month:attempt; a Pending replay reuses that key and row. R3 Precondition: a unit with a Paid row, including a manual fixture, cannot be charged. R4 Postcondition: success sets the attempt to Paid and decline to Failed; an interruption leaves Pending. R5 Retry invariant: a Failed attempt permits exactly one next attempt only after RETRY_DELAY_DAYS, within MAX_PAYMENT_ATTEMPTS and within the same billing month.

## 7 Edge cases

Interruption after fake-processor success and before saving Paid; repeated runs on the same date; a manual payment posted before the first run; decline immediately before or at the retry boundary; schedule created on or after the selected day; unsupported method or month; integer fields supplied as booleans.

## 8 Decisions and open questions

D1 The runner is serialized in the local harness. It stores Pending before calling the fake; replay applies the durable result. A PostgreSQL test schema stores schedules/payments; a separately committed fake-processor key store survives the injected application restart. Tests exercise the real persistence boundary. A manual fixture is inserted before execution, never during it.

D2 For a billing month, the chosen due date must be strictly later than the schedule’s UTC creation date. The runner is eligible from that due date through month end, allowing catch-up. Creating a schedule on or after this month’s chosen day makes its first due date next month. The harness runs only today’s billing month and rejects unresolved earlier-month attempts as setup errors. Exhausted attempts remain Failed; no cross-month retry is defined.

D3 All amounts are integer cents from the community fixture. now() supplies UTC timestamps. History lists all attempts by unit_id, then attempt, then id. A valid future month returns an empty list. The local fixtures select RETRY_DELAY_DAYS ≥ 1 and MAX_PAYMENT_ATTEMPTS ≥ 1; tests read those settings and create dates with room for the retry in the same month.

D4 Validate identity/access, then body shape, method, day and token. Missing/extra fields or wrong types (including bool for day) return Invalid request body. Require method=test_card or return Unknown method; integer day 1–28 or return Invalid day; nonblank trimmed token or return Token is required. After valid input, an existing unit schedule returns 409 Schedule already exists. Month must be YYYY-MM with month 01–12. Manual fixtures have attempt=1, key ending in :manual and processor_id=null.

D5 Fake tokens are synthetic constants: succeed always succeeds; decline_first declines attempt 1 and succeeds later; other nonblank tokens decline. Each new key persists its result and processor_id="fake:"+key before returning. Replays ignore token changes and return that stored result.
