# S-1 — draft for team review

Source: M1 Review v3, section 5. Contract wording preserved. Human approval pending. Descriptions of planned tests refer to the source document baseline; see current test files and test-baseline evidence for execution state.

## 1 Problem

Residents ask about work already handled and visit the office because they cannot see status (E-1, E-2, E-12). The first slice exposes submission and status retrieval through FastAPI. Portal adoption remains A-1.

## 2 Scope

A seeded resident submits a request for their own unit, lists their own requests in that community and reads one request by ID. Tests call the API directly. This is a local API prototype, not the finished web interface.

## 3 Non goals

No status-update endpoint, reopening, photos, deletion or editing. No production authentication or email. No tenant or board-wide access policy. X-User-Id is a local test identity selector used only with synthetic seeded users.

## 4 Interface

All endpoints accept X-User-Id: str. RequestOut fields are listed in section 5; submitted_by is omitted from the public response. Errors have exactly {"detail": message}. GET responses are externally observable acceptance-test outputs.

| Endpoint | Typed input and return | Possible errors |
| --- | --- | --- |
| POST /communities/{community_id}/requests | community_id: int; body {category: str, description: str}; 201 → RequestOut | 401 Unknown user; 404 Not found; 422 Invalid request body / Description is required / Description is too long / Unknown category |
| GET /communities/{community_id}/requests | community_id: int; 200 → list[RequestOut] | 401 Unknown user; 404 Not found |
| GET /requests/{request_id} | request_id: int; 200 → RequestOut | 401 Unknown user; 404 Not found |

## 5 Data

PostgreSQL is the intended local store, selected through DATABASE_URL. Liquibase SQL changesets create the schema. Each test uses a disposable database or schema. All identifiers are positive integers; foreign keys must exist. Timestamps are UTC strings formatted YYYY-MM-DDTHH:MM:SSZ in responses.

| Entity | Fields and constraints |
| --- | --- |
| Community | id: int, unique; name: str, 1–100 characters, unique. |
| Unit | id: int, unique; community_id: int; label: str, 1–20 characters, unique per community. |
| User and Membership | User.id: int, unique. Membership: user_id: int; community_id: int; role: str in resident, board_member, manager, admin; unit_id: int \| null, required for resident and belonging to that community. One membership per user/community. |
| Request | id: int, system-generated; community_id: int; unit_id: int; submitted_by: int; category: str in REQUEST_CATEGORIES; description: str, trimmed, 1–MAX_DESCRIPTION_CHARS characters; status: str in Open, In progress, Resolved; created_at: UTC timestamp. The API supplies identity, unit, status and time. |

## 6 Rules

R1 Invariant: a returned request belongs to a community where the caller is a resident and has submitted_by equal to that caller. R2 Invariant: a missing or unauthorized request produces the same 404 response and no details. R3 Preconditions: POST requires resident membership and a valid category and description. R4 Postcondition: a successful POST creates exactly one Open request and returns it at the injected time. R5 Postcondition: a rejected POST changes no request or request list.

## 7 Edge cases

Whitespace-only or oversized descriptions; a valid description padded with whitespace; category case mismatch; cross-community and same-community neighbor IDs; missing or invalid identity; malformed JSON and malformed path IDs; equal creation timestamps.

## 8 Decisions and open questions

D1 Validation order is caller, path and membership, body shape, description, category. The first failure wins. Missing, non-numeric or unknown X-User-Id returns 401 Unknown user. IDs must match ^[1-9][0-9]*$; a malformed path or unauthorized community returns 404 Not found. The body must be a JSON object containing exactly category and description as strings; missing, extra or mistyped fields return 422 Invalid request body.

D2 Trim with Python str.strip() and measure with len(). An empty trimmed description returns 422 Description is required; an oversized one returns 422 Description is too long. Categories match exactly and case-sensitively; otherwise return 422 Unknown category. Tests select a category from REQUEST_CATEGORIES and use MAX_DESCRIPTION_CHARS, rather than hard-coding unresolved limits.

D3 List order is created_at descending, then id descending, without pagination. Creation time comes from app.clock.now() -> datetime with UTC tzinfo, replaced in tests. The provisional self-only visibility rule is A-6; broader access is OQ2.

D4 The harness seeds communities, units, users and memberships through app/seed.py; seed operations are not API endpoints. AC-6 sets status through test fixtures only. Files are app/main.py, app/models.py, app/requests.py, app/settings.py, app/clock.py and db/changelog/. Migration commands are part of the test command; no runtime schema guessing is allowed.

OQ1 How should an authorized tenant be linked to a unit and given request access (Q-5, Q-12)? Do not build anything that depends on this. Stop and ask.

OQ2 Should another resident of the same unit or a board member see requests they did not submit (Q-7)? Do not build anything that depends on this. Stop and ask.
